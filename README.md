# JobBoard · AI 原生的多阶段流程管理工具

> **西南大学 · 谷昊林 · 个人作品**
>
> 不是「给日历加个 AI 助手」，而是**重新设计流程管理的操作路径**。
> 一句话创建整条阶段链，一句话批量调整日程——同时保留精确的手动操作能力。

---

## 一、这类问题长什么样

**有一类任务，结构完全相同：**

> **N 个对象** × 每个对象 **M 个阶段** × 每个阶段 **各自的截止时间**

比如：

| 场景 | 对象 | 阶段链 |
|---|---|---|
| **产品研发** | 智能仓储系统_上线 | 需求评审 → 方案设计 → 开发联调 → 测试回归 → 正式发布 |
| **科研申报** | 国自然青年基金_申报 | 选题论证 → 初稿撰写 → 单位内审 → 系统提交 → 会评答辩 |
| **学术投稿** | ICML 2027_投稿 | 实验补全 → 论文成稿 → 内部预审 → 系统投稿 → Rebuttal |
| **招投标** | XX 项目_投标 | 资格预审 → 标书撰写 → 内部评审 → 递交投标 → 开标 |
| **活动筹备** | 学术年会_举办 | 征稿 → 审稿 → 日程编排 → 会务准备 → 现场执行 |

**它们的共同痛点是**：当「对象数 × 阶段数」超过 20 条时，**维护日程本身变成了一种负担**。

| 要做的事 | 传统工具的操作 |
|---|---|
| 新建一条完整流程 | 点新建 → 填标题 → 选日期 → 保存 → **重复 5 次** |
| 把某个阶段推迟两天 | 找到 → 点开 → 改日期 → 保存 |
| 把今天所有事挪到明天 | **一条一条改** |

## 二、为什么套用通用日程工具不好用

**因为这些场景的用户表达，本来就是高度结构化的。**

> 「帮我建一个产品上线流程：需求评审、方案设计、开发联调、测试回归、正式发布」

**这句话里的信息，本来就足够填满一整条流程链。** 之所以要用户手点 5 次，纯粹是因为传统界面只能接受表单输入。

**这就是本产品的切入点。**

## 三、AI 原生的交互设计

### 3.1 核心判断：把「操作」重新定义为「表达」

**传统方案**：用户适应系统 → 系统定义交互路径（表单、按钮、下拉框）

**本产品**：系统适应用户 → **用户用自然语言表达意图，Agent 翻译成结构化操作**

```
用户: "帮我建一个产品上线流程：需求评审、方案设计、开发联调、测试回归、正式发布"

Agent: 我准备创建以下流程：
       · 智能仓储系统_上线
       · 需求评审 / 方案设计 / 开发联调 / 测试回归 / 正式发布
       [✅ 确认执行]  [❌ 取消]
```

**这不是「加了个聊天框」——交互路径本身变了。**

从「用户拆解任务 → 逐条执行」，变成「用户描述目标 → 确认结果」。

### 3.2 关键设计：AI 和 UI 各做各擅长的事

**一个常见的错误做法是「全面 AI 化」——把所有操作都塞进对话框。**

我判断这不对：

| 操作类型 | 特征 | 交给谁 |
|---|---|---|
| **批量、意图明确** | 「把明天的事往后推一天」 | ✅ **Agent** —— 一句话替代 N 次点击 |
| **精确、可视化** | 「把开发联调从周三下午挪到周五上午」 | ✅ **日历拖拽** —— 看见再操作，更直观 |
| **模糊、需确认** | 「帮我安排一下剩下的阶段」 | ✅ **Agent 出方案 + 用户确认** |

**所以产品同时保留了两条路径，而且它们共享同一份数据。**

```
        ┌─────────────┐
        │  Agent 对话  │ ←── 自然语言意图
        └──────┬──────┘
               │
        ┌──────▼──────┐
        │   SQLite    │ ←── 单一数据源，双轨读写，始终一致
        └──────┬──────┘
               │
        ┌──────▼──────┐
        │  日历 / 事件流 │ ←── 拖拽、点击编辑
        └─────────────┘
```

> **数据一致性是核心设计约束**：对话改了日程，UI 立刻反映；UI 拖了节点，Agent 下次操作时读到的是最新状态。

## 四、核心难题：AI 会出错，产品怎么兜底？

**这是整个项目里我最花心思的部分。**

Agent 能操作数据库，意味着它有「写权限」。**而 LLM 不可靠——它会幻觉、会凭记忆编造、会对着已经不存在的计划继续操作。**

**我的原则是：不能指望模型自觉，必须用产品机制兜住它。**

设计了五道防线：

### ① 两阶段确认 —— 防「AI 擅自改数据」

**所有写操作，Agent 必须先输出执行计划，用户确认后才真正执行。**

```
Agent 输出计划 + [CONFIRM] 标记
   → 前端渲染「确认 / 取消」按钮
   → 用户点击确认 → 才调用工具
```

**产品判断**：读操作（查询）可以直接执行——错了也没损失；**写操作必须拦截**——因为数据被改了，用户很难察觉。

### ② 取消即清除 —— 防「AI 对着废案继续操作」

用户点了「取消」，如果只是界面上隐藏了那条计划消息，**LLM 下次还会看到它，可能继续基于废案执行。**

**解法**：取消的计划消息标记为 `cancelled`，**在发给 LLM 前过滤掉**。

> 这是一个典型的「产品细节决定 AI 可靠性」的例子——**界面上看不见 ≠ 模型看不见**。

### ③ 强制刷新数据 —— 防「AI 凭记忆操作」

Agent 每次操作前，**必须先查询数据库最新状态**，不能基于对话历史里的旧信息行动。

### ④ 结构化返回，不让模型猜 —— 防「张冠李戴」

查询节点时，SQL 用 **JOIN 直接返回 `subject` 字段**，而不是只返回 `application_id` 让模型自己去对应。

**产品判断**：**凡是能用系统算出来的，就不要让模型推理。** 模型推理的每一步都是幻觉风险。

### ⑤ Prompt 硬约束 —— 防「从记忆里拼凑」

明确要求：**流程名、阶段名必须从本轮工具返回结果中逐字复制，禁止从历史对话或自身记忆中拼凑。**

## 五、产品完整度

除了 AI 能力，一个能真正用起来的产品还需要：

| 能力 | 说明 |
|---|---|
| **日历视图** | 周视图，AM/PM 双时段，超期节点标红 |
| **事件流视图** | 按流程分组，链式展示阶段进度（待办/完成/跳过） |
| **拖拽排期** | 日历上直接拖动节点改时间 |
| **点击编辑** | 弹窗修改名称、日期、时段、状态 |
| **级联删除** | 删除阶段时可选删除其后续所有节点 |
| **AI 自动排期** | 在「今天」到「截止日」之间均匀分布，AM/PM 交替 |
| **防重复** | 流程名唯一标识，数据库索引 + 代码双层校验 |
| **演示数据预埋** | 数据库为空时自动播种 3 条**不同场景**的演示流程 |

## 六、技术实现

| 层级 | 技术选型 | 为什么 |
|---|---|---|
| **前端** | Next.js 14 (App Router) + React 18 + TypeScript + TailwindCSS | 前后端一体，部署简单 |
| **后端** | Next.js API Routes | 无需独立服务 |
| **数据库** | SQLite (better-sqlite3) | 零配置，本地即跑 |
| **LLM** | DeepSeek Chat API | 成本低，Function Calling 支持好 |
| **Agent** | **纯手写 ReAct 循环** | 见下 |
| **部署** | Docker + Zeabur | — |

### 为什么手写 ReAct 而不用 LangChain

**约 280 行代码实现完整 Agent 循环**（messages 构建 → API 调用 → tool_calls 解析 → 工具执行 → 结果回填）。

**理由**：这个场景的 Agent 逻辑很清晰（6 个工具 + 确认机制），引入框架带来的抽象成本大于收益。**手写反而让「确认机制」「取消过滤」这些定制逻辑更容易实现。**

### 六个 Function Calling 工具

| 工具 | 类型 | 功能 |
|---|---|---|
| `create_application` | 写 | 创建流程（流程名 + 完整阶段链） |
| `update_stage` | 写 | 更新阶段（日期、时段、状态） |
| `bulk_shift` | 写 | 批量移动（某天 / 某流程的事件整体偏移） |
| `auto_schedule` | 写 | 自动排期（均匀分布 + AM/PM 交替） |
| `list_applications` | 读 | 列出所有流程及阶段 |
| `list_stages_in_range` | 读 | 按日期范围查询（JOIN 返回流程名） |

## 七、快速开始

```bash
npm install
cp .env.local.example .env.local   # 填入 DEEPSEEK_API_KEY
npm run dev                        # 访问 http://localhost:3000
```

**Docker**：

```bash
docker build -t jobboard .
docker run -p 3000:3000 -e DEEPSEEK_API_KEY=sk-xxx jobboard
```

| 环境变量 | 必填 | 默认值 | 说明 |
|---|---|---|---|
| `DEEPSEEK_API_KEY` | ✅ | — | DeepSeek API 密钥 |
| `DEEPSEEK_MODEL` | ❌ | `deepseek-chat` | 模型名称 |
| `DB_PATH` | ❌ | `./data/jobboard.db` | SQLite 路径 |

## 八、这个项目教会我的

**做 AI 产品，「能不能做出来」不是最难的部分，「怎么让它可靠」才是。**

我一开始的思路是「把 Agent 能力做大」——加更多工具、支持更复杂的操作。

**后来发现真正的问题在另一头**：Agent 越强，它能造成的破坏越大。**用户不敢用一个会擅自改数据的助手。**

**所以我把重心从「增强能力」转到了「建立信任」**——五道防线里没有一道是让 AI 变聪明的，全都是**让它出错时不造成损失**。

**这个判断，是我做这个项目最大的收获：**

> **AI 产品的核心竞争力，不在于模型能做什么，而在于产品敢让它做什么。**
